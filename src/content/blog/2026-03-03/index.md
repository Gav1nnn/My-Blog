## 前言

写 Go 服务时，很多人都会先感受到一个现象：

- goroutine 可以开很多
- 线程数量却不一定跟着暴涨
- 网络连接很多时，程序也不一定马上被线程阻塞拖死
- 同样是并发模型，Go 写起来往往比“线程 + 锁 + 回调”更自然

这些现象背后，其实都绕不开 Go runtime 的调度器。

如果只停留在表面，可以简单说一句：

> Go 用 goroutine 做用户态并发，再用 runtime 负责调度。

但这句话还不够。

真正值得理解的是：

> Go 为什么需要自己的一套调度器？它到底做了什么，才让 goroutine 看起来既轻量，又能支撑高并发网络场景？

这一篇就沿着这条主线，梳理 Go 的 GMP 模型、任务队列、work stealing、系统调用切换、抢占和 netpoll。

## 一、为什么 Go 不能只靠操作系统线程调度？

如果没有 goroutine，最直接的并发模型就是：

```text
一个任务 → 一个线程
```

这个模型不是不能用，而是很快会遇到几个问题：

- 线程创建和销毁成本高
- 线程切换要经过内核调度，代价不低
- 每个线程都需要独立栈空间
- 大量线程阻塞在 IO 上时，资源浪费严重

对于服务端程序来说，真正常见的情况不是“少量特别重的任务”，而是：

- 大量请求
- 大量短任务
- 大量网络读写等待

这类场景如果直接一对一绑定线程，成本会很高。

所以 Go 做了一个关键设计：

> 让 goroutine 作为用户态的轻量任务存在，再由 runtime 在少量线程上复用执行这些 goroutine。

这也是 Go 调度器存在的起点。

## 二、G、M、P 分别是什么？

Go 调度器最核心的模型就是 GMP。

很多资料会直接背定义，但更重要的是理解三者各自解决什么问题。

### 1. G：goroutine，本质是待执行的任务

`G` 代表 goroutine。

它可以理解成：

- 一段要执行的 Go 代码
- 它自己的栈
- 它的运行状态和上下文

所以 `G` 本质上不是线程，而是 Go runtime 管理的任务单元。

### 2. M：machine，对应真正的系统线程

`M` 代表真正干活的执行者，本质上对应一个操作系统线程。

最终跑在 CPU 上的，不是 goroutine 本身，而是线程。

所以可以把 `M` 理解成：

- 真正向操作系统申请来的执行资源
- 最终负责在 CPU 上执行 Go 代码

### 3. P：processor，是调度器运行时资源

`P` 是 GMP 里最容易被忽略、但也最关键的一层。

它不是 CPU 本身，也不是线程。

更准确地说，`P` 代表的是：

- 调度上下文
- 本地可运行队列
- 与执行相关的一些本地资源

例如一个 `P` 上会维护自己的本地 goroutine 队列，而线程 `M` 想执行 goroutine，必须先拿到一个 `P`。

所以从职责上可以简单理解成：

| 角色 | 本质 |
|---|---|
| `G` | 要执行的任务 |
| `M` | 真正执行任务的线程 |
| `P` | 让调度器高效运转起来的本地资源与上下文 |

## 三、为什么一定需要 P，而不是只有 G 和 M？

这是理解 GMP 的关键。

如果没有 `P`，模型就会退化成 `GM`：

```text
goroutine 任务池
  ↓
多个线程直接竞争任务
```

看起来很简单，但问题也很明显：

- 所有线程都要去抢同一个全局任务队列
- 全局锁竞争会很重
- 本地缓存和本地队列无法建立
- 调度和内存分配都更难做局部优化

而 `P` 的存在，本质上是在做一件事：

> 把高频调度操作尽量本地化，减少所有线程都去抢全局资源。

可以把它理解成：

- 没有 `P`：大家都去中央仓库抢任务
- 有了 `P`：每个人先从自己的本地仓库拿，只有本地空了才去中央协调

这就是为什么 `P` 不只是一个“中间层名词”，而是 Go 调度器性能能做起来的核心设计。

### 1. P 上最重要的资源是什么？

从理解调度器的角度，最重要的是这两个：

- 本地可运行队列
- 执行调度所需的本地上下文

这意味着大多数情况下，一个线程 `M` 绑定一个 `P` 之后，可以优先直接从这个 `P` 的本地队列拿 `G` 执行，而不需要频繁碰全局锁。

### 2. P 的数量和什么有关？

`P` 的数量通常由 `GOMAXPROCS` 决定。

它限制的是：

> 同一时刻最多有多少个 goroutine 可以并行地占用 CPU 执行 Go 代码。

这也是为什么很多人说：

- goroutine 数量可以远大于线程数
- 真正决定 CPU 并行度上限的关键参数之一，是 `GOMAXPROCS`

## 四、goroutine 到底是怎么被调度起来的？

有了 G、M、P 之后，还要继续问一个问题：

> 一个新的 goroutine 被创建之后，最终是怎么跑起来的？

可以粗略理解为下面这条链路：

```text
go func() 创建 G
  ↓
优先进入当前 P 的本地队列
  ↓
M 绑定 P
  ↓
M 从 P 的本地队列取 G 执行
  ↓
G 执行结束或被切走
  ↓
M 继续取下一个 G
```

### 1. 本地队列优先

新建 goroutine 时，通常优先进入当前 `P` 的本地队列。

这一步很重要，因为它意味着：

- 新任务尽量本地消化
- 减少进入全局队列的频率
- 减少锁竞争

### 2. 全局队列兜底

如果本地队列满了，或者某些场景下需要全局协调，goroutine 也会进入全局队列。

所以全局队列并没有消失，它仍然存在，只是：

> Go 不希望所有调度都围绕全局队列展开。

### 3. M 的调度循环

线程 `M` 在拿到一个 `P` 之后，会进入一个持续循环：

1. 先看当前 `P` 的本地队列
2. 本地没有，再尝试全局队列
3. 还没有，再考虑从其他 `P` 偷取
4. 或者去看 netpoll 有没有就绪的网络事件

这也是为什么 Go 调度器不是“调一次就结束”，而是一个持续找活干的循环系统。

## 五、work stealing 为什么重要？

如果某个 `P` 的本地队列空了，最直觉的做法是让它闲着，等新任务进来。

但这会导致非常差的资源利用率。

Go 的做法是引入 work stealing，也就是工作窃取：

> 当一个 `P` 本地没有可运行的 goroutine 时，它会尝试从其他 `P` 的本地队列里偷一部分任务过来执行。

这样做解决了两个问题：

### 1. 负载不均衡

如果某些 `P` 很忙、某些 `P` 很闲，不做任务迁移，就会出现：

- 有的 CPU 核心忙不过来
- 有的 CPU 核心却闲着

work stealing 可以把负载重新拉平。

### 2. 降低线程和调度资源浪费

如果本地没活就直接让线程睡死，系统会频繁进入“休眠 - 唤醒 - 再找活”的状态。

work stealing 能让已经存在的执行资源优先复用起来，而不是动不动就创建和销毁线程。

所以它不是一个“锦上添花”的小技巧，而是 Go 调度器维持吞吐和利用率的重要机制。

## 六、goroutine 发生阻塞系统调用时，为什么 P 要交出去？

这是 GMP 里最关键的工程设计之一。

如果一个 goroutine 执行的是普通 Go 代码，它跑在哪个线程上，线程就继续执行它。

但如果 goroutine 进入了阻塞系统调用，比如某些磁盘 IO、网络系统调用或其他阻塞 syscall，问题就来了：

- goroutine 所在的线程 `M` 可能会被内核卡住
- 如果 `M` 还一直占着 `P`
- 那这个 `P` 上本来能继续运行的其他 goroutine 也跟着没法推进

这显然不合理。

所以 Go 的思路是：

> 当线程 `M` 因为阻塞 syscall 卡住时，runtime 会尽量把 `P` 从这个 `M` 手里摘出来，交给其他可运行的线程继续调度 goroutine。

这就是很多资料里说的 syscall handoff 或 hand off 机制。

### 1. 这件事解决了什么问题？

它解决的是：

> 不要让“线程阻塞”直接演变成“调度能力整体掉线”。

因为真正宝贵的不只是线程，而是“能继续调度 Go 代码的能力”。

如果不把 `P` 交出去，那么一个阻塞 syscall 就可能把整个执行通路卡住。

### 2. 阻塞结束后会怎样？

当阻塞 syscall 返回后，原来的线程 `M` 如果还要继续运行相关 goroutine，就需要重新尝试获取可用的 `P`。

如果当下拿不到 `P`，那它也不会强行抢占整个系统，而是进入后续调度流程。

所以这里真正被保护的是：

- `P` 不要被无意义地长期占住
- 其他可运行 goroutine 能继续往前推进

## 七、为什么 Go 还需要抢占？

如果只有“任务进队列 -> M 执行 -> 执行完再切换”这一套机制，调度器仍然会遇到一个问题：

> 如果某个 goroutine 长时间不主动让出执行权，会不会把别人饿住？

答案是会。

这就是为什么 Go 还需要抢占机制。

### 1. 没有抢占会发生什么？

如果一个 goroutine：

- 计算时间很长
- 不发生阻塞
- 也没有进入明显的调度点

那它就可能长时间占着 CPU。

后果就是：

- 其他 goroutine 等待时间变长
- 调度公平性变差
- 延迟尾部更差

对于在线服务来说，这种问题很致命，因为服务更怕“少数任务一直霸占执行权”。

### 2. 抢占本质上在解决什么？

抢占机制要解决的是：

> 不要让某个 goroutine 因为一直跑得动，就无限期占用 CPU。

它不是为了让程序“更炫”，而是为了让调度器维持基本公平性。

所以可以把抢占理解成：

- 给长时间运行的 goroutine 设置边界
- 让 runtime 有机会重新做调度决策
- 避免其他 goroutine 饥饿

## 八、netpoll 是怎么把网络 IO 接进调度器的？

理解到这里，GMP 还只解释了“CPU 上的任务怎么调度”。

但 Go 服务里还有一个更现实的问题：

> 大量 goroutine 并不是一直在跑 CPU，它们很多时候只是在等网络 IO。

如果每个 goroutine 等网络时都把一个线程卡住，那 Go 并发能力还是会很快碰到上限。

所以 Go runtime 还需要一层 netpoll。

### 1. netpoll 是什么？

netpoll 可以理解成 Go runtime 内部的网络轮询器。

它的作用是：

- 监听 fd 的 IO 就绪事件
- 当某个 goroutine 因网络读写暂时无法继续时，把它挂起
- 等 fd 就绪后，再把这个 goroutine 放回可运行队列

也就是说，netpoll 本质上是在做一件事：

> 把“网络事件就绪”转换成“某个 goroutine 可以继续运行”。

### 2. goroutine 做网络读写时会发生什么？

可以粗略理解成这个流程：

```text
goroutine 发起网络读写
  ↓
如果 fd 暂时未就绪
  ↓
runtime 把 fd 交给 netpoll 监听
  ↓
当前 goroutine 挂起
  ↓
线程 M 去执行别的 goroutine
  ↓
fd 就绪
  ↓
netpoll 把对应 goroutine 重新标记为 runnable
  ↓
调度器再次把它安排运行
```

这也是为什么 Go 网络代码看起来像阻塞式同步写法：

```go
n, err := conn.Read(buf)
```

但底层并不等于“一个连接卡住一个线程”。

### 3. select / poll / epoll 在这里是什么角色？

这里简单提一下 Linux 侧的背景就够了。

操作系统需要一种机制，让少量线程同时监听大量 fd 的就绪状态，这就是 IO 多路复用。

大致的演进方向可以理解为：

- `select`：早期方案，fd 数量有限，且每次要线性扫描
- `poll`：去掉了固定上限，但仍然要遍历全部 fd
- `epoll`：事件驱动，只返回就绪 fd，更适合大量连接场景

Go runtime 并不是自己重新发明了一套网络事件系统，而是：

> 在 Linux 上基于 `epoll`，在 macOS/BSD 上基于 `kqueue`，再往上封装成 netpoll，并把它接进 goroutine 调度体系。

所以这篇的重点不是 Linux 内核细节，而是要理解：

> netpoll 让 Go 把“IO 等待”从“线程阻塞问题”转换成了“goroutine 挂起和唤醒问题”。

## 九、GMP 和 netpoll 放在一起，Go 才真正能支撑高并发

单独看 GMP，它解决的是：

- goroutine 如何在少量线程上被高效调度
- 本地队列、全局队列和 work stealing 如何协作
- 阻塞 syscall 不要拖垮整体调度能力

单独看 netpoll，它解决的是：

- 网络 IO 不要把线程大量卡死
- fd 就绪后，如何重新唤醒 goroutine

把这两者接在一起，Go 才真正形成了一套完整模型：

```text
CPU 计算任务 → GMP 调度
网络等待任务 → netpoll 挂起/唤醒
两者最终统一回到 goroutine 的 runnable 调度体系
```

这也是 Go 在后端服务里很强的一点：

> 开发者写的是同步风格代码，但 runtime 在底层把 CPU 调度和网络事件都做了协同处理。

## 十、这对后端开发到底意味着什么？

理解 Go 调度器，不只是为了知道几个 runtime 名词。

更重要的是，它会直接影响你怎么看服务表现。

### 1. goroutine 很多，不等于线程很多

goroutine 是任务单元，不是线程本身。

所以看到 goroutine 数量很多时，不要立刻等同于“线程一定爆了”，而应该继续判断：

- 这些 goroutine 是在跑 CPU，还是在等 IO
- 是否存在大量阻塞
- 是否有 goroutine 泄漏

### 2. CPU 密集型和 IO 密集型服务，瓶颈并不一样

如果服务主要是 CPU 密集型任务，问题更可能出在：

- `GOMAXPROCS`
- 调度竞争
- 抢占和长时间运行任务

如果服务主要是 IO 密集型任务，问题更可能出在：

- 网络等待
- 连接管理
- netpoll 唤醒与调度链路

### 3. 排查问题时要有调度器视角

很多现象如果没有调度器视角，会看得很碎。

比如：

- goroutine 为什么越来越多
- 为什么线程数没很多，但延迟还是高
- 为什么 syscall 一多，吞吐开始掉
- 为什么大量连接挂着时，服务并没有立刻崩

这些问题背后，很多都能回到 GMP 和 netpoll 这条主线上解释。

## 结语

Go 调度器这套设计，核心并不是“名字很多”，而是它把几个关键问题拆开处理了：

- `G` 负责表示任务
- `M` 负责真正执行
- `P` 负责把调度资源本地化
- work stealing 负责平衡负载
- syscall handoff 负责避免阻塞线程拖垮调度
- 抢占负责保证公平性
- netpoll 负责把网络 IO 接回 goroutine 调度体系

如果只记一句话，我更建议记这个版本：

> Go 并不是单纯“协程很多所以快”，而是 runtime 在任务调度、线程复用、阻塞切换和网络事件处理这几件事上，做了成体系的工程设计。

也正因为有这套设计，Go 才特别适合写大量并发、网络密集、又希望保持同步编码风格的后端服务。
