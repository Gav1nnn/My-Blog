## 前言

写 Go 代码时，slice 几乎是你最常用的数据结构之一。

但它也是最容易让人产生错觉的一类东西。

比如：

- 为什么把 slice 传进函数之后，改元素外面也会变？
- 为什么 `append` 之后，有时候外面的 slice 也像被改了，有时候又完全没反应？
- 为什么只保留了一个很小的子切片，内存却迟迟下不来？
- 为什么很多“看起来没什么问题”的代码，最后都能追到 slice 的底层行为？

这些现象表面上很零散，背后其实都指向同一个事实：

> slice 不是数组本身，而是对底层数组的一段描述。

也正因为这个设计，slice 在 Go 里既高效又灵活，但也很容易让人误判代码行为。

这一篇就沿着这条主线，梳理 slice 的底层结构、函数传参、`append`、扩容，以及它为什么会带来隐藏 bug 和内存问题。

## 一、slice 到底是什么？

先说最关键的一点：

> slice 不是动态数组本身，它更像是“数组窗口”。

你可以把 slice 理解成一个描述结构，里面通常有三部分信息：

- 指向底层数组的指针
- 当前长度 `len`
- 当前容量 `cap`

可以先用一个简化图理解：

```text
slice
  ├─ ptr ───────┐
  ├─ len        │
  └─ cap        │
                ↓
        underlying array
        [a][b][c][d][e]
```

这意味着：

- 真实数据存在底层数组里
- slice 本身更像一个“我现在能看到哪一段数据”的描述符

所以你平时写的：

```go
s := []int{1, 2, 3}
```

表面看是在创建一个 slice，实际上更准确的理解是：

- runtime 准备了一段底层数组
- `s` 持有了这段数组对应的一份 slice 描述

这一点非常重要，因为后面很多看起来“诡异”的行为，其实都来自这里。

## 二、为什么 slice 既像值类型，又总让人感觉像引用？

很多人第一次学 Go 时，最容易在这里绕进去。

因为从直觉上看：

- slice 传进函数以后，改元素外面能看到
- 多个 slice 之间经常互相影响

所以很多人会下意识说：

> slice 是引用传递。

但这个说法不准确。

### 1. Go 的函数传参，本质上都是值传递

在 Go 里，函数调用时传进去的永远是一个值的副本。

不管你传的是：

- `int`
- `struct`
- `array`
- `pointer`
- `slice`
- `map`
- `channel`

本质上都发生了一次值拷贝。

所以更准确的说法应该是：

> Go 里没有“这个类型天生就是按引用传递”这种分类，真正发生的是“传进函数的是一个值，而这个值本身是否带有访问外部底层数据的能力”。 

### 2. 为什么 slice 看起来像“引用传递”？

因为 slice 这个值内部，本来就包含了一个指向底层数组的指针。

也就是说，函数参数拿到的虽然是 slice header 的副本，但这个副本里的指针，仍然指向同一块底层数组。

举个例子：

```go
func change(s []int) {
	s[0] = 100
}
```

调用：

```go
nums := []int{1, 2, 3}
change(nums)
fmt.Println(nums) // [100 2 3]
```

为什么外面变了？

不是因为发生了“引用传递”，而是因为：

- `nums` 的 slice header 被复制了一份给 `s`
- `s` 和 `nums` 这两个 header
- 都指向同一块底层数组

所以函数里改的是数组元素，自然会反映到外面。

### 3. 什么会共享，什么不会共享？

理解 slice 传参时，一个很好用的区分方式是：

- **改底层数组中的元素**：可能会影响外部
- **改 slice header 自身**：不会直接改外部那个 header

比如：

```go
func changeLen(s []int) {
	s = s[:1]
}
```

这里函数里修改的是 `s` 这个副本自己的 `len/cap` 视图，而不是外部变量本身。

所以外面的 slice 不会因为这句重新切片就自动变短。

这也是为什么很多人会觉得 slice “一半像值，一半像引用”。

其实它既不是神秘的混合物，也不是例外规则，而是：

> 传递的是 slice 描述符副本，但这个描述符可能仍然共享同一块底层数组。

## 三、`append` 到底做了什么？

slice 真正最容易让人踩坑的地方，不是切片语法，而是 `append`。

因为 `append` 的行为不是永远一致的，它至少有两条路径。

### 1. 容量还够：直接复用原底层数组

如果当前 slice 的 `cap` 还足够，`append` 通常会直接把新元素写到原底层数组后面。

例如：

```go
s1 := make([]int, 2, 4)
s1[0], s1[1] = 1, 2

s2 := append(s1, 3)
```

这时更接近的情况是：

```text
s1 -> [1 2 _ _]
s2 -> [1 2 3 _]
```

`s1` 和 `s2` 仍然可能共享同一块底层数组，只是看到的长度不同。

这也是为什么有些场景下，后续对 `s2` 的修改会间接影响到和它共享底层数组的其他 slice。

### 2. 容量不够：分配新数组，再拷贝旧数据

如果 `append` 发现 `len == cap`，继续追加已经放不下，就会触发扩容。

这时 runtime 会做几件事：

1. 分配一块更大的新数组
2. 把旧数据拷贝过去
3. 把新元素写进去
4. 返回一个指向新数组的新 slice

这就意味着：

- `append` 前后两个 slice
- 可能从同一块底层数组
- 分叉成指向两块不同数组

例如：

```go
func grow(s []int) {
	s = append(s, 4)
	fmt.Println(s)
}

nums := []int{1, 2, 3}
grow(nums)
fmt.Println(nums)
```

这里函数里的 `s` 是否和外部 `nums` 分叉，取决于 `append` 时有没有扩容。

这就是很多 slice bug 的根源：

> 你以为自己只是“往后加一个元素”，但底层可能已经不是原来那块数组了。

## 四、为什么函数里 `append` 之后，外面的结果经常和预期不一样？

这一节其实是在把前两节真正收束起来。

很多人最困惑的就是这种代码：

```go
func add(s []int) {
	s = append(s, 4)
}
```

然后外面调用：

```go
nums := []int{1, 2, 3}
add(nums)
fmt.Println(nums)
```

外面为什么没看到新元素？

原因有两层。

### 1. 外部变量没有被重新赋值

函数里拿到的是 slice header 的副本。

即使 `append` 返回了一个新的 slice，这个新 slice 也只是赋给了函数内部的局部变量 `s`。

外面的 `nums` 并没有接住这个返回值。

### 2. 扩容可能让内外彻底分叉

如果 `append` 触发了扩容，那么函数内部的 `s` 已经指向新数组，而外部 `nums` 仍然指向旧数组。

所以：

- 改旧数组上的元素，外部可能看得见
- `append` 后的新结果，如果不返回出去，外部就不一定能拿到

这也是为什么更稳妥的写法通常是：

```go
func add(s []int) []int {
	return append(s, 4)
}

nums = add(nums)
```

因为你明确地把“可能已经变化的 slice 描述符”重新交回给了调用方。

## 五、扩容机制为什么值得关心？

很多文章一写扩容，就开始背倍率。

比如：

- 小于某个阈值时按 2 倍增长
- 大于某个阈值时按较小比例增长

这些细节在不同 Go 版本里可能会有调整。

对写业务代码的人来说，更重要的不是死记倍率，而是理解：

> 扩容意味着重新分配内存和拷贝数据，它不是免费操作。

### 1. 扩容的直接代价

一旦扩容，至少会发生两类成本：

- 申请新内存
- 把旧数据拷贝到新数组

如果这个动作出现在高频路径里，比如：

- 请求编解码
- JSON 解析
- 日志拼接
- 大量中间结果收集

那它就不只是“多拷贝了一下”，而是会进一步带来：

- 更多堆分配
- 更多短命对象
- 更高 GC 压力

### 2. 为什么 `make([]T, 0, n)` 很常见？

因为当你大致知道结果规模时，提前预留容量可以减少扩容次数。

例如：

```go
items := make([]string, 0, 100)
```

这样做的意义不是“写法更高级”，而是：

- 降低重复扩容概率
- 减少内存拷贝
- 减少热点路径上的分配开销

所以扩容机制值得关心，不是为了背源码细节，而是为了理解：

> slice 的方便不是没有代价，它的代价往往体现在你看不见的分配和拷贝上。

## 六、slice 为什么很容易引发隐藏 bug？

理解了共享底层数组和 `append` 之后，就能更容易看懂一些常见坑。

### 1. 多个 slice 共享同一底层数组

例如：

```go
base := []int{1, 2, 3, 4}
a := base[:2]
b := base[1:3]
```

这时候 `a` 和 `b` 虽然是两个 slice 变量，但它们并不是彼此独立的数据副本。

它们很可能只是同一块底层数组上的不同窗口。

所以一个地方改元素，另一个地方也可能被影响。

### 2. 子切片意外持有大数组

这是很典型的内存问题来源。

比如你从一个很大的字节数组里，只取了一小段：

```go
small := big[:10]
```

如果 `small` 还活着，那它背后的整个 `big` 底层数组也可能继续活着。

哪怕你实际上只关心前 10 个字节。

这件事和你前面那篇 GC 文章其实是直接连着的：

> GC 只看对象是否还可达，不会因为你“只用了一小部分”就自动替你释放整块大数组。

所以如果你真的只需要很小的一段数据，往往要主动拷贝出来：

```go
tmp := make([]byte, 10)
copy(tmp, big[:10])
```

这样旧的大数组才更有机会被回收。

### 3. 函数里 `append` 之后，行为突然分叉

前面已经分析过，这类问题很典型：

- 没扩容时，可能还共享旧数组
- 扩容后，函数内外直接分叉

这类 bug 的难点在于，它不是语法错，而是：

> 代码看起来很自然，但底层语义已经悄悄变了。

### 4. 一边遍历，一边改结构

比如边 `range` 边 `append`，或者一边保留旧 slice，一边把新 slice 往后传。

这类代码不一定马上报错，但很容易让结果变得不直观。

原因还是一样：

- 你以为自己在操作“一个数组”
- 实际上你在操作“多个共享或分叉的视图”

## 七、slice 对性能和内存意味着什么？

slice 之所以是 Go 里非常成功的设计，恰恰是因为它在很多场景下兼顾了：

- 使用方便
- 分配成本低
- 共享底层数据的高效率

但这些优点同时也意味着，你需要知道它的代价在哪里。

### 1. 共享底层数组有时很高效

如果只是对同一块数据做不同窗口视图，slice 的确非常高效。

因为它避免了：

- 额外复制
- 额外分配

这也是它在很多场景下比“每次都复制一份新数组”更实用的原因。

### 2. 共享底层数组有时也很危险

同样因为它共享底层数组，所以会带来：

- 数据互相污染
- 生命周期被意外拉长
- 大数组无法及时释放

所以 slice 的高效和风险，其实来自同一个根源。

### 3. 热点路径里的 slice 使用方式会影响 GC

如果你的代码在热点路径里：

- 反复扩容
- 制造很多短命 slice
- 保留对大数组的小引用

那它最终都会回到两个问题：

- 堆分配是否变多了
- GC 压力是否变大了

所以 slice 并不只是一个容器问题，它也会直接变成内存管理问题。

## 八、写 Go 代码时应该怎么用 slice？

理解了前面的机制之后，很多实践建议就不是“经验口诀”，而是自然推出来的结论。

### 1. 需要隔离数据时，主动 `copy`

如果你明确不希望多个 slice 共享底层数组，那就不要赌“刚好不会互相影响”。

直接拷贝会更稳：

```go
dst := make([]int, len(src))
copy(dst, src)
```

### 2. 已知规模时，尽量提前预估容量

如果你大致知道会追加多少元素，提前 `make` 一个合适容量的 slice，通常比一路被动扩容更好。

### 3. 在函数边界上，要意识到自己传递的是 slice 描述符副本

也就是说：

- 改元素，可能影响外部
- 改 header，不会直接改外部
- `append` 之后，如果调用方要继续拿最新结果，最好返回新 slice

### 4. 对大数组切片要警惕“只用一点点却一直占整块”

这类问题很隐蔽，但对长生命周期服务尤其重要。

### 5. 不要默认多个 slice 彼此独立

只要它们来自同一块底层数组，就要默认它们存在共享关系，除非你已经主动做了隔离。

## 结语

slice 难的地方，从来都不是语法。

真正难的是它的语义：

> 它看起来像数组，实际上是数组窗口；看起来像引用，实际上传递的又是一个值类型的描述符。

也正因为这层设计，slice 在 Go 里才会同时具备两面性：

- 一方面它非常高效、好用、适合工程实践
- 另一方面它又很容易在共享、扩容和生命周期上制造隐藏问题

如果只记一句话，我更建议记这个版本：

> slice 的很多坑，不是因为它特殊，而是因为你以为自己拿到的是“数据本体”，实际上你拿到的是“指向底层数组的一段视图”。

一旦把这个前提想清楚，很多看起来反直觉的行为，其实都会变得顺理成章。
