## 前言

上一篇讲 `map` 时，我们遇到了一个很典型的并发问题：

> 多个 goroutine 共享同一份可变数据时，必须通过锁或其他同步机制保护它。

这条路没有问题。

但当系统里开始出现大量并发任务，仅仅围绕共享数据不断加锁，代码很容易变成这样：

- 谁可以修改这份数据？
- 修改前应该拿哪把锁？
- 锁的范围应该多大？
- 一个任务完成后，怎么通知下一个任务？
- 上游不再产生数据时，下游怎么退出？

这些问题里，有些是在保护共享状态，有些其实是在协调任务。

Go 的 `channel` 主要解决的是后者：

> 让 goroutine 通过发送和接收数据完成协作，同时把等待、唤醒和部分同步关系交给 runtime 管理。

所以 `channel` 不只是一个并发安全队列。

它同时表达了三件事：

- 数据从谁手里交给谁
- 发送方和接收方什么时候可以继续执行
- 一组 goroutine 应该如何协作和退出

这一篇就沿着这条主线，梳理 `channel` 的通信语义、底层结构、阻塞与唤醒，以及它为什么既能让并发代码更清晰，也很容易造成 goroutine 泄漏。

## 一、Channel 解决的不是“传值”这么简单

先看一个最简单的例子：

```go
ch := make(chan int)

go func() {
    ch <- 42
}()

value := <-ch
fmt.Println(value)
```

表面上，这段代码只是把数字 `42` 从一个 goroutine 传给另一个 goroutine。

但发送和接收背后，还发生了一次协作：

- 发送方准备好数据
- 接收方等待数据
- runtime 让两边完成交接
- 交接完成后，goroutine 才继续执行

这和把值写进一个共享变量不一样。

如果使用共享变量，需要自己解决可见性和同步问题：

```go
var value int
var done bool

go func() {
    value = 42
    done = true
}()
```

这段代码不能保证另一个 goroutine 看到一致的 `value` 和 `done`。

你还需要锁、原子操作或其他同步机制。

而通过 `channel` 完成的发送与接收，本身就建立了同步关系。

接收方成功收到值时，可以确认对应发送操作已经发生。

所以 `channel` 的价值不只是移动数据，而是：

> 用一次明确的通信，替代一部分隐含的共享状态协调。

## 二、不要通过共享内存来通信，应该怎么理解？

Go 并发里经常会出现一句话：

> Do not communicate by sharing memory; instead, share memory by communicating.

它并不是说 Go 代码不能使用锁，也不是说所有共享状态都必须改成 `channel`。

更准确的理解是：

> 当多个 goroutine 的关系本质上是任务交接或数据流转时，优先把这种关系直接表达成通信，而不是让它们共同修改一堆状态。

比如一个任务处理流程：

```text
读取任务 -> 处理任务 -> 保存结果
```

可以让三个阶段分别拥有自己的职责，再通过 `channel` 传递任务：

```text
reader -> jobs channel -> worker -> results channel -> writer
```

这样做的好处是：

- 数据流向明确
- 每个阶段的职责更集中
- 等待和唤醒由 channel 表达
- 更容易限制同时处理的任务数量

但如果只是保护一份共享缓存，`map + Mutex` 往往更直接。

所以不能简单理解成：

```text
channel 比锁更高级
```

真正应该判断的是：

```text
这是共享状态问题，还是任务协作问题？
```

共享状态通常适合锁。

任务交接、结果汇聚、事件通知和背压控制，通常更适合 `channel`。

## 三、无缓冲 Channel：发送和接收必须完成一次交接

创建无缓冲 channel：

```go
ch := make(chan int)
```

它没有存放数据的缓冲区。

所以一次发送要完成，必须有接收方参与；一次接收要完成，也必须有发送方参与。

可以把它理解成一次面对面的交接：

```text
sender -- value --> receiver
```

如果只有发送方：

```go
ch := make(chan int)
ch <- 1
```

当前 goroutine 会阻塞，因为没有接收者。

如果只有接收方：

```go
ch := make(chan int)
value := <-ch
```

当前 goroutine 同样会阻塞，因为没有发送者。

无缓冲 channel 的关键不是“容量为零”，而是它提供了一种同步语义：

> 发送完成，意味着某个接收方已经接过了这个值。

因此它很适合表达：

- 两个 goroutine 之间的直接交接
- 等待某个任务产生结果
- 确认另一个 goroutine 已经执行到某个阶段

但这种同步关系也意味着，只要配对关系设计错了，就很容易阻塞。

## 四、有缓冲 Channel：允许有限程度的速率差

创建有缓冲 channel：

```go
ch := make(chan int, 3)
```

它可以暂时存放三个元素。

只要缓冲区还没满，发送方就可以把数据放进去并继续执行，不需要等待接收方立刻出现。

```text
sender -> [value][value][ ] -> receiver
```

这让发送方和接收方可以有一定程度的速率差。

比如：

- 上游偶尔产生一小波任务
- 下游处理速度有轻微波动
- 希望发送方不必每次都等待接收方

但缓冲区不是无限队列。

当缓冲区满了，新的发送仍然会阻塞。

当缓冲区空了，新的接收仍然会阻塞。

所以有缓冲 channel 的本质可以理解成：

> 在发送方和接收方之间加入一个容量有限的等待区。

这个“有限”非常重要。

它让 channel 可以自然形成背压：

```text
下游处理不动
    ↓
缓冲区逐渐填满
    ↓
上游发送开始阻塞
    ↓
系统不再无限制积压任务
```

如果只是为了让代码“不阻塞”而随意把缓冲区开得很大，问题通常只是被延后了。

积压的数据仍然要占用内存，处理延迟也仍然存在。

所以缓冲区大小应该表达系统能够容忍的积压量，而不是一个随手填写的数字。

## 五、Channel 底层维护了什么？

从 runtime 视角看，channel 底层由一个类似 `hchan` 的结构维护。

不展开每个字段，可以先抓住几个核心部分：

```text
hchan
  ├─ buf       环形缓冲区
  ├─ qcount    当前缓冲区中的元素数量
  ├─ dataqsiz  缓冲区容量
  ├─ sendx     下一个发送位置
  ├─ recvx     下一个接收位置
  ├─ sendq     等待发送的 goroutine 队列
  ├─ recvq     等待接收的 goroutine 队列
  ├─ closed    是否已关闭
  └─ lock      保护 channel 内部状态
```

其中，缓冲区通常可以理解成一个环形队列。

当发送方写入数据时，`sendx` 向前移动。

当接收方取走数据时，`recvx` 向前移动。

到达尾部后，它们会重新绕回开头：

```text
[A][B][ ][ ]
       ↑     ↑
     recvx sendx
```

这样可以复用已经腾出的空间，不需要每次发送和接收都移动整段数据。

等待队列则负责记录暂时不能继续执行的 goroutine：

- `sendq`：想发送，但当前无法完成发送
- `recvq`：想接收，但当前没有可接收数据

等待中的 goroutine 会通过 runtime 的 `sudog` 结构挂到相应队列上。

这也说明了一件事：

> channel 不只是存储数据，它还维护着正在围绕这些数据等待的 goroutine。

## 六、一次发送到底会发生什么？

执行：

```go
ch <- value
```

runtime 会根据 channel 当前状态选择不同路径。

### 1. 已经有接收方在等待

如果 `recvq` 里已经有接收方等待，发送方可以直接把数据交给它，并让对应 goroutine 恢复为可运行状态。

这时不需要先把数据留在缓冲区里，再让接收方取走。

数据完成交接后，发送方可以继续执行。

### 2. 没有接收方，但缓冲区还有空间

如果是有缓冲 channel，并且缓冲区没满，数据会被写入环形缓冲区。

发送方不需要等待接收者立刻处理，可以继续运行。

### 3. 没有接收方，缓冲区也没有空间

这时发送不能立即完成。

当前 goroutine 会被记录到 `sendq`，然后进入等待状态。

```text
sender
  ↓
sendq
  ↓
等待接收方取走数据或腾出空间
```

直到有接收操作让发送条件重新满足，runtime 才会唤醒它。

### 4. Channel 已经关闭

向已关闭的 channel 发送数据会触发 `panic`：

```go
close(ch)
ch <- value // panic: send on closed channel
```

因为关闭表达的是：

> 后续不会再有新的值发送进来。

关闭之后继续发送，违反了这个约定。

## 七、一次接收到底会发生什么？

执行：

```go
value := <-ch
```

同样会根据 channel 状态走不同路径。

### 1. 缓冲区里有数据

接收方取走缓冲区中的下一个元素。

如果此时还有发送方因为缓冲区已满而等待，runtime 可以在取走元素后推进等待中的发送操作，让缓冲区继续流转。

### 2. 没有缓冲数据，但已经有发送方等待

接收方可以直接从等待中的发送方完成数据交接，并唤醒发送方。

无缓冲 channel 的发送和接收主要就是通过这种方式配对。

### 3. 没有数据，也没有发送方

接收暂时无法完成。

当前 goroutine 会进入 `recvq` 等待，直到有发送方提供数据，或者 channel 被关闭。

### 4. Channel 已经关闭

关闭 channel 后，接收方仍然可以先读完缓冲区里已有的数据。

缓冲区清空后，继续接收会立即返回元素类型的零值。

为了区分“真的收到了一个零值”和“channel 已经关闭且没有数据”，可以使用：

```go
value, ok := <-ch
```

其中：

- `ok == true`：收到一个有效发送的值
- `ok == false`：channel 已关闭，并且已没有数据可读

这也是 `for range` 能在 channel 关闭并清空后结束的原因：

```go
for value := range ch {
    fmt.Println(value)
}
```

## 八、阻塞 Channel 时，线程也会一起被卡住吗？

当 goroutine 因 channel 操作无法继续时，runtime 会把它挂起。

可以简化理解成：

```text
无法发送或接收
    ↓
goroutine 加入等待队列
    ↓
runtime 挂起当前 goroutine
    ↓
M 去执行其他可运行 goroutine
```

底层会涉及 `gopark` 和 `goready` 这类 runtime 机制：

- `gopark`：让当前 goroutine 进入等待状态
- `goready`：让满足条件的 goroutine 重新进入可运行状态

这和前面 GMP 文章里的调度器正好接上。

goroutine 因 channel 阻塞，不等于对应操作系统线程必须一直空等。

runtime 可以让线程继续执行其他可运行任务。

当 channel 条件满足后，被唤醒的 goroutine 会重新进入调度体系，等待获得执行机会。

所以 channel 能成为 Go 并发模型的一部分，不只是因为它提供了语法：

```go
ch <- value
value := <-ch
```

更重要的是：

> 它的阻塞与唤醒直接接入了 Go runtime 的 goroutine 调度。

## 九、close 表达的是“不会再发送”，不是释放资源

`close(ch)` 经常被误解成文件的 `Close`：

```text
关闭 channel = 释放 channel
```

这并不准确。

channel 和其他 Go 对象一样，不再被引用时可以由 GC 回收。

关闭 channel 的主要语义是：

> 通知接收方，这个 channel 之后不会再产生新的值。

因此关闭通常应该由能够确定“不会再发送”的一方负责。

最典型的是单一发送方：

```go
func produce(ch chan<- int) {
    defer close(ch)

    for i := 0; i < 3; i++ {
        ch <- i
    }
}
```

接收方只需要持续读取，直到 channel 关闭：

```go
for value := range ch {
    fmt.Println(value)
}
```

“由发送方关闭”不是语言强制规则，而是一条所有权原则。

因为只有发送方最清楚是否还会继续发送。

如果有多个发送方，关闭会复杂很多。

仅仅用 `sync.Once` 防止重复 `close`，并不能自动避免其他发送方在关闭后继续发送。

更稳的方式通常是：

- 由一个协调者等待所有发送方结束，再统一关闭
- 使用 `WaitGroup` 确认所有生产者已经退出
- 使用独立的取消信号或 `Context` 通知生产者停止

关闭设计的重点不是“怎么保证 close 只执行一次”，而是：

> 怎么保证关闭发生时，确实已经不会再有发送操作。

## 十、nil Channel 和已关闭 Channel 有什么不同？

channel 的几种状态有完全不同的行为。

| 操作 | `nil` channel | 正常 channel | 已关闭 channel |
| --- | --- | --- | --- |
| 发送 | 永久阻塞 | 根据接收方和缓冲区决定 | `panic` |
| 接收 | 永久阻塞 | 根据发送方和缓冲区决定 | 读完缓冲区后返回零值和 `false` |
| 关闭 | `panic` | 成功关闭 | 再次关闭会 `panic` |

为什么 `nil` channel 的发送和接收会永久阻塞？

因为它没有对应的底层 channel 结构，也就永远不可能出现匹配的发送方、接收方或缓冲区状态变化。

这听起来只像陷阱，但 `nil channel` 也可以被有意识地用于动态关闭某个通信分支。

不过这需要和 `select` 配合，具体行为更适合留到下一篇展开。

## 十一、Channel 为什么容易造成 goroutine 泄漏？

channel 本身通常不是传统意义上的内存泄漏来源。

真正危险的是：

> goroutine 因 channel 永久阻塞，导致它自己以及它持有的对象一直无法释放。

例如：

```go
func result() <-chan int {
    ch := make(chan int)

    go func() {
        ch <- calculate()
    }()

    return ch
}
```

如果调用方最终没有接收这个结果，内部 goroutine 会永远阻塞在发送上。

它的栈以及引用的对象都会继续存活。

常见泄漏场景包括：

- 发送方永远等不到接收方
- 接收方永远等不到发送方
- `for range` 等待一个永远不会关闭的 channel
- pipeline 下游提前退出，上游仍然尝试发送
- 后台 goroutine 没有取消和退出路径

解决这类问题，不能只盯着 channel 容量。

更重要的是在创建 goroutine 时就回答：

- 它正常情况下怎么结束？
- 调用方提前退出时，谁通知它停止？
- 发送或接收可能阻塞时，有没有取消路径？
- 谁负责关闭 channel？

比如可以通过 `Context` 提供退出信号：

```go
func produce(ctx context.Context, ch chan<- int) {
    for {
        value := nextValue()

        select {
        case ch <- value:
        case <-ctx.Done():
            return
        }
    }
}
```

这里 `select` 的作用是让发送操作和取消信号同时参与等待。

具体的选择规则和底层机制，会在后续文章单独展开。

## 十二、Channel、锁和普通队列应该怎么选？

实际开发里，不应该为了“更像 Go”就把所有逻辑都改成 channel。

它们解决的问题不同。

### 1. 保护共享状态：优先考虑锁

比如：

- 并发访问一个 map
- 更新结构体中的多个关联字段
- 保护一段必须原子完成的业务逻辑

这类问题使用 `Mutex` 或 `RWMutex` 通常更直接。

### 2. 任务交接和结果汇聚：优先考虑 Channel

比如：

- worker pool 分发任务
- 多个 goroutine 汇总结果
- pipeline 在阶段之间传递数据
- 通知某个任务已经完成

这类问题的核心是 goroutine 之间的协作，channel 更容易表达数据流向。

### 3. 需要持久化、重试或跨进程：Channel 不够

channel 只存在于当前 Go 进程内。

它不提供：

- 持久化
- 跨进程通信
- 消息确认
- 消费重试
- 服务重启后的恢复

如果任务不能随着进程退出而丢失，就应该考虑 Kafka、RabbitMQ 或其他消息系统，而不是把 channel 当成进程内消息队列的无限放大版。

## 十三、写 Go 并发代码时，怎么更稳地使用 Channel？

使用 channel 时，可以抓住几个原则。

### 1. 先明确通信所有权

在创建 channel 时就确定：

- 谁负责发送
- 谁负责接收
- 谁知道发送已经结束
- 谁负责关闭

所有权越模糊，关闭和退出逻辑越容易出问题。

### 2. 每个 goroutine 都应该有退出路径

不要只考虑正常数据流。

还要考虑：

- 请求取消
- 上游失败
- 下游提前结束
- 服务关闭

一个没有退出路径的 goroutine，通常就是未来的泄漏点。

### 3. 缓冲区要表达容量边界

有缓冲 channel 可以缓解短期速度差，但不能解决长期消费不足。

如果缓冲区持续填满，真正的问题通常是：

- 下游处理能力不足
- 上游没有限流
- 任务设计不合理

这时应该解决吞吐和背压问题，而不是继续扩大容量。

### 4. 不要为了避免阻塞而滥用 goroutine

这种写法看起来能让发送立即返回：

```go
go func() {
    ch <- value
}()
```

但如果没有接收方，只是把阻塞转移到了一个新的 goroutine。

调用方看不到阻塞，不代表阻塞消失了。

大量这样创建的 goroutine 会变成泄漏和内存压力。

## 结语

`channel` 的语法非常简单：

```go
ch <- value
value := <-ch
close(ch)
```

但它真正解决的问题不只是传值。

它把数据交接、任务同步、等待队列和 goroutine 调度连接在了一起：

- 无缓冲 channel 表达直接交接
- 有缓冲 channel 允许有限的速率差并形成背压
- 等待队列记录暂时无法继续的 goroutine
- runtime 负责阻塞和唤醒
- `close` 通知接收方不会再有新值

所以理解 channel，不是为了把锁全部替换掉，而是为了判断：

> 当前问题到底是在保护共享状态，还是在组织 goroutine 之间的协作？

当问题是共享状态时，锁通常更清晰。

当问题是数据流转、任务交接和生命周期协调时，channel 才真正体现出它作为 Go 并发原语的价值。
