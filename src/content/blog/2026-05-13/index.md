## 前言

前两篇文章主要梳理了 AI、LLM、Agent 的整体关系，以及神经网络、Transformer、Token、Embedding、Attention 等基础概念。

这一篇开始进入更贴近后端开发者的方向：RAG。

RAG，全称 Retrieval-Augmented Generation，中文叫检索增强生成。

它可以理解为：

> 让大模型在回答问题之前，先去外部知识库中检索相关资料，再基于资料生成答案。

对于后端开发者来说，RAG 是切入大模型应用非常好的方向。

> 因为它不只是模型调用，还涉及文件上传、文档解析、异步任务、向量数据库、权限隔离、流式响应、日志监控等大量后端工程能力。

## 一、为什么需要 RAG？

大语言模型虽然能力很强，但它有几个明显问题。

### 1. 不知道企业私有知识

大模型训练时使用的是公开或通用数据。

它并不知道某个公司的内部文档、业务规则、接口说明、项目资料、用户手册等内容。

例如你问模型：

> 我们公司教务系统里的老师绑定流程是什么？

如果这些资料没有公开出现在训练数据里，模型是不可能准确知道的。

> **问题本质**：大模型的参数包含了大量通用知识，但并不包含企业的私有数据。

### 2. 知识可能过期

模型训练完成后，参数基本固定。

如果某些知识在训练之后发生变化，模型可能不知道最新情况。

例如：

- 公司制度更新了
- 接口文档改了
- 产品功能变了
- 数据库表结构调整了
- 项目部署方式升级了

> **关键问题**：模型的知识更新周期非常长，通常是几个月甚至几年，而企业内部变化可能是每天、每周都在发生。

### 3. 容易产生幻觉

当模型不知道答案时，它有时不会直接说”不知道”，而是生成一个看起来很合理但实际错误的回答。

这就是常说的幻觉问题。

> **真实案例**：
> - 医疗系统：模型可能捏造不存在的治疗方案
> - 金融系统：可能给出错误的投资建议
> - 客服系统：可能承诺做不到的服务

> 如果是在普通聊天场景，这可能只是回答不准。
> 但如果是在企业知识库、客服、医疗、金融、法律、运维系统里，幻觉可能会造成严重后果。

### 4. 上下文窗口有限

一种简单做法是把所有文档都塞进 Prompt。

但这很快会遇到问题：

- 文档太长，超过上下文窗口（GPT-4 128K，Claude 200K，但成本很高）
- Token 成本太高（1K Token ≈ 0.002美元）
- 响应延迟变大
- 关键信息被淹没
- 模型可能抓不住重点

所以我们需要一种方式：

> 不要把所有资料都给模型，
> 而是先检索出最相关的片段，
> 再交给模型生成回答。

这就是 RAG 的基本思路。

> **成本对比**：
> - 传统方式：塞入 100K Token，成本 0.2美元/请求
> - RAG 方式：检索 5 个片段 ≈ 2K Token，成本 0.004美元/请求
> **相差 50 倍！**

## 二、RAG 的核心流程

RAG 的核心流程可以理解为：

```
用户问题
  ↓
问题向量化
  ↓
向量数据库检索相关文档片段
  ↓
把片段拼接进 Prompt
  ↓
LLM 基于资料生成回答
```

> 它不是让模型凭空回答，而是让模型参考检索出来的资料进行回答。

一个典型 RAG 系统通常分成两个阶段：

### 离线阶段：数据准备与索引

```
上传文档 → 解析文档 → 文本清洗 → 文档切片 → 生成 Embedding → 写入向量数据库 → 保存元数据
```

**主要任务**：
- 数据解析与处理：读取PDF、Word、Markdown、HTML等不同格式的文档
- 文档分块（Chunking）：将长文档切分成小块（Chunk），以便更精确地定位知识
- 向量化（Embedding）：使用向量模型将文本块转换为数值向量
- 数据入库（Vector Storage）：将向量和原文内容存储到向量数据库中（如 Chroma, Pinecone, Milvus）

### 在线阶段：检索与生成

```
用户提问 → 问题向量化 → 向量检索 TopK → Rerank（可选）→ 构造 Prompt → 调用 LLM → 流式返回结果
```

**主要任务**：
- 用户查询理解：对用户输入的提问进行语义分析、查询改写或优化
- 向量化查询：将用户的问题也转换为向量
- 语义检索（Retrieval）：在向量数据库中匹配与问题语义最接近的前K个知识块
- 重排（Rerank）：优化检索结果，对知识块进行相关性重新排序，提高答案质量
- 答案生成（Generation）：将”问题+检索到的知识”一起发送给大语言模型（LLM），由LLM总结生成最终答案

## 三、Embedding 和向量检索是什么关系？

RAG 的核心能力之一是语义检索。

语义检索依赖 Embedding。

Embedding 可以把文本转成向量，使得文本之间可以计算相似度。

例如：

```
“Go 的 goroutine 是什么？” → [0.21, -0.11, 0.36, ...]
“Go 协程的原理是什么？” → [0.19, -0.09, 0.34, ...]
```

因为这两个问题语义接近，所以它们的向量距离也会比较近。

这就是语义检索的基础。

### 传统搜索 vs 向量检索

| 传统关键词搜索 | 向量语义搜索 |
|---|---|
| 精确匹配字面词 | 匹配语义相似的内容 |
| “Redis 缓存雪崩” | “Redis 怎么避免大面积失效” |
| 需要了解专业术语 | 不需要了解专业术语 |
| 容易漏掉相关内容 | 能找到语义相关内容 |
| 实现简单 | 需要向量数据库 |

### 实际应用案例

**用户问**：
> Redis 怎么避免缓存大面积失效？

**文档中写**：
> 缓存雪崩可以通过随机 TTL、热点数据预热、多级缓存等方式缓解。

虽然用户没说”缓存雪崩”，但向量检索仍可能召回相关内容。

> **优势体现**：
> 1. 用户可以用自己的语言提问
> 2. 不需要知道文档中的专业术语
> 3. 可以处理表达方式的多样性

## 四、RAG 的离线阶段：文档入库

一个典型知识库问答系统，通常会先有离线处理流程。

离线阶段主要处理文档入库：
```text
上传文档
  ↓
解析文档
  ↓
文本清洗
  ↓
文档切片 Chunk
  ↓
生成 Embedding
  ↓
写入向量数据库
  ↓
保存文档元数据
```

### 1. 上传文档

用户可能上传：

- PDF
- Word
- Markdown
- TXT
- HTML
- 表格
- 接口文档
- 项目说明文档

后端需要处理文件大小限制、文件类型校验、存储路径、上传状态等问题。

> **工程要点**：不同文件格式需要不同的解析策略，解析质量直接影响后续检索效果。

### 2. 解析文档

不同文档格式需要不同解析方式。

例如：

| 文档类型 | 解析策略 |
|---|---|
| PDF | 提取文本，处理页眉页脚 |
| Word | 解析段落、标题结构 |
| Markdown | 按标题层级处理 |
| HTML | 提取正文，过滤标签 |
| 表格 | 考虑行列语义关联 |
| 代码文档 | 保留代码块格式 |

文档解析质量会直接影响后续检索质量。

如果原始文本提取就有问题，后面 Embedding 和检索也会受影响。

### 3. 文本清洗

解析出来的文本通常需要清洗。

例如：

- 去掉多余空格
- 去掉无意义页眉页脚
- 处理乱码
- 保留标题结构
- 处理特殊符号
- 合并断行

文本清洗看似不起眼，但对 RAG 效果影响很大。

> **注意**：如果清洗过度，可能会丢失重要语义信息；如果清洗不足，又可能引入噪声干扰检索。

### 4. 文档切片 Chunk

大模型上下文有限，向量检索也不适合直接把整篇文档作为一个向量。

所以需要把文档切成多个片段，也就是 Chunk。

一个 Chunk 不能太长，也不能太短。

| Chunk 太长的问题 | Chunk 太短的问题 |
|---|---|
| 检索不够精确 | 上下文不完整 |
| Prompt 容易变大 | 语义容易丢失 |
| 关键信息可能被淹没 | 模型回答时缺少背景 |

所以实际工程中常会结合：

- 固定长度切片
- 按标题切片
- 按段落切片
- 滑动窗口
- Chunk overlap 重叠区域

> **常用策略**：通常 Chunk 长度在 500-1000 Token，overlap 设置为 10%-20%。
### 5. 生成 Embedding

每个 Chunk 都需要调用 Embedding 模型，生成对应向量。

例如：
```text
Chunk 文本 → Embedding 模型 → 向量
```

这一步可能比较耗时，所以通常适合放到异步任务中处理。

> **工程建议**：可以使用 MQ 消息队列处理批量 Embedding 任务，避免阻塞主请求链路。

### 6. 写入向量数据库

生成向量后，需要写入向量数据库。

常见选择包括：

| 开源方案 | 商业方案 | PostgreSQL 扩展 |
|---|---|---|
| Milvus | Pinecone | pgvector |
| Qdrant | Weaviate Cloud | pgvector++ |
| Weaviate | Zilliz | - |

> **选型建议**：小项目可以用轻量方案（如 pgvector）完成 MVP，生产环境再考虑专业向量数据库。

### 7. 保存文档元数据

除了向量，还需要保存文档元数据。

例如：

- 文档 ID
- 文件名
- 文件类型
- 上传用户
- 所属知识库
- Chunk 内容
- Chunk 顺序
- 解析状态
- 创建时间
- 更新时间

这些通常可以存储在 MySQL 中。

> **架构建议**：向量数据库负责相似度检索，MySQL 负责业务元数据管理，职责分离更清晰。

## 五、RAG 的在线阶段：用户问答

在线阶段主要处理用户提问：
```text
用户提问
  ↓
问题改写或增强
  ↓
生成问题 Embedding
  ↓
向量检索 TopK
  ↓
必要时 Rerank
  ↓
构造 Prompt
  ↓
调用 LLM
  ↓
流式返回结果
```

### 1. 用户提问

用户输入自然语言问题，例如：

> 老师怎么绑定学生？

系统需要判断这个问题属于哪个知识库、哪个用户、是否有权限访问相关文档。

### 2. 问题向量化

系统调用 Embedding 模型，把用户问题转成向量。
```text
用户问题 → Embedding 模型 → 问题向量
```

### 3. 向量检索 TopK

然后用问题向量去向量数据库中检索最相似的文档片段。
```text
问题向量 → 向量数据库 → TopK 相关 Chunk
```

TopK 表示返回最相似的前 K 个片段。

| K 值太小的问题 | K 值太大的问题 |
|---|---|
| 召回不够，可能漏掉相关信息 | 增加 Prompt 长度 |
|  | 引入噪声，影响回答质量 |

> **常用值**：TopK 通常设置为 5-10，具体需要根据实际情况调优。

### 4. Rerank 重新排序

有些系统会在初步召回后，再使用 Rerank 模型重新排序。

大致流程是：
```text
向量检索召回 20 个片段
  ↓
Rerank 模型重新判断相关性
  ↓
选出最相关的 5 个片段
```

Rerank 可以提升最终进入 Prompt 的资料质量。

> **效果对比**：向量检索 + Rerank 的组合通常比纯向量检索的准确率更高，但会增加推理延迟。

### 5. 构造 Prompt

检索到相关片段后，需要把它们拼接进 Prompt。

例如：

```
你是一个知识库问答助手。
请只根据下面的资料回答用户问题。
如果资料中没有答案，请回答”不知道”。

资料：
[片段1]
[片段2]
[片段3]

用户问题：xxx
```

Prompt 设计会直接影响回答质量。

> **关键**：Prompt 要明确告诉模型只基于提供的资料回答，避免模型产生幻觉。

### 6. 调用 LLM 生成回答

LLM 会基于检索出来的资料生成最终回答。

理想情况下，模型应该：

- 基于资料回答
- 不编造资料中没有的内容
- 可以引用来源
- 回答清晰、简洁、可读

> **期望效果**：好的 RAG 系统，模型应该能够明确区分"来自资料的答案"和"自己的推断"。
### 7. 流式返回结果

为了提升用户体验，很多系统会使用流式响应。

也就是模型一边生成，后端一边把内容返回给前端。

这样用户不需要等待完整回答生成完毕，可以更快看到输出。

> **用户体验**：流式响应可以显著减少用户感知的延迟，特别是在生成长文本时效果明显。

## 六、从后端工程视角看 RAG 系统

从后端工程视角看，一个 RAG 系统并不是简单地”调用大模型 API”。

它通常可以拆成几个模块。

> **核心观点**：RAG 不是模型能力，而是一个完整的后端工程系统。

### 1. 文档管理模块

负责：

- 文件上传
- 文档列表
- 文档删除
- 文档状态管理
- 文档元数据存储

一般可以用 MySQL 存储文档元数据，例如文件名、文件类型、上传用户、解析状态、创建时间等。

### 2. 文档解析与切片模块

负责：

- PDF / Word / Markdown / TXT 解析
- 文本清洗
- Chunk 切分
- Chunk 与原文位置映射
- 大文档异步处理

这里可以结合 MQ 做异步任务，把耗时的文档解析和向量化过程从主请求链路中拆出去。

> **异步处理**：大文档解析可能耗时较长，建议使用消息队列异步处理，避免阻塞用户请求。

### 3. Embedding 与向量存储模块

负责：

- 调用 Embedding 模型
- 生成文本向量
- 写入向量数据库
- 建立文档片段和向量之间的映射

向量数据库可以选择 Milvus、Qdrant、Weaviate、pgvector 等，也可以在小项目中先用更轻量的方案完成 MVP。

### 4. 检索模块

负责：

- 问题向量化
- TopK 相似度检索
- 关键词检索
- 混合召回
- Rerank 排序
- 权限过滤

这一层直接影响 RAG 的回答质量。

很多时候，RAG 回答不好，不一定是模型不行，而是召回的资料不对。

> **关键点**：检索质量比模型选择更重要。如果召回了错误的内容，再好的模型也无法给出正确答案。

### 5. 对话与生成模块

负责：

- Prompt 构造
- 上下文管理
- 调用 LLM
- 流式响应
- 输出引用来源
- 记录会话历史

这部分和用户体验关系很大。

如果支持流式输出，用户会更快看到响应，不需要一直等待完整结果生成完毕。

### 6. 权限与租户隔离模块

如果是企业知识库，权限非常重要。

系统需要保证：

- 用户只能检索自己有权限的文档
- 不同团队的数据不能串
- 私有知识库不能被其他用户召回
- 管理员可以管理组织内文档
- 普通用户只能访问授权范围内的内容

这部分非常适合体现后端工程能力。

> **安全原则**：RAG 系统的权限控制应该在检索层实现，而不是在结果返回后过滤。

### 7. 监控与评估模块

RAG 系统还需要监控：

- 模型调用耗时
- Token 消耗
- Embedding 成本
- 向量检索耗时
- 召回命中率
- 用户反馈
- 失败请求
- 流式响应中断情况

这些能力决定了系统是否真的可上线、可维护、可优化。

## 总结

RAG 是后端开发者切入大模型应用非常好的方向。

它解决了大模型的几个核心问题：

| 问题 | 解决方案 |
|---|---|
| 不知道私有知识 | 接入企业知识库 |
| 知识可能过期 | 随时更新文档 |
| 容易产生幻觉 | 基于资料回答 |
| 上下文窗口有限 | 检索相关片段 |
| 直接塞全文成本太高 | 精准召回降低成本 |

它的核心流程是：
```text
文档入库
  ↓
生成 Embedding
  ↓
向量检索
  ↓
构造 Prompt
  ↓
LLM 生成回答
```

从工程角度看，RAG 不是简单调 API，而是一个完整的后端系统。

它涉及文件上传、文档解析、异步任务、向量数据库、MySQL、Redis、MQ、权限隔离、流式响应、日志监控等能力。
