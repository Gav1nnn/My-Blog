## 前言

前面几篇文章分别介绍了：

- AI、LLM、Agent 的整体关系
- 神经网络、Transformer、Token、Embedding、Attention 等基础概念

这一篇继续往上走，开始理解 Agent。

Agent 是现在大模型应用中非常高频的概念。

但刚开始接触时，很容易把 Agent 理解成”聊天机器人”或者”套壳大模型”。

实际上，Agent 的关键不只是聊天，而是：

> 让大模型具备理解任务、调用工具、使用知识、维护记忆、执行流程的能力。

也就是说，Agent 不只是回答问题，而是尝试完成任务。

## 一、Agent 和普通聊天机器人有什么区别？

普通聊天机器人更多是：
```text
用户输入 → LLM 生成回答
```

它主要负责对话和文本生成。

而 Agent 更像是：
```text
用户输入
  ↓
理解任务
  ↓
规划步骤
  ↓
检索知识
  ↓
调用工具
  ↓
观察结果
  ↓
继续决策
  ↓
返回最终答案或执行结果
```

> **核心区别**：普通聊天机器人负责"说"，Agent 负责做。

举个例子。

如果用户问：

> Redis 缓存雪崩怎么解决？

普通聊天机器人可以直接根据已有知识回答。

但如果用户说：

> 帮我查一下上周失败的订单，并总结失败原因，然后发给运营同学。

这就不是单纯聊天了。

Agent 需要：

1. 理解任务
2. 判断时间范围是上周
3. 调用订单查询工具
4. 获取失败订单数据
5. 分析失败原因
6. 生成报告
7. 调用通知工具发送给运营同学

这就是 Agent 和普通聊天机器人的区别。

Agent 不只是”会说”，还要”会做”。

## 二、LLM 是 Agent 的大脑

LLM 负责理解用户意图、分析上下文、生成计划和组织输出。

例如用户说：

> 帮我查一下上周失败的订单，并总结失败原因。

LLM 需要理解：
```text
时间范围：上周
查询对象：订单
筛选条件：失败订单
后续任务：总结失败原因
```

这一步类似 Agent 的”大脑理解”。

但是，LLM 本身不能直接访问你的数据库，也不能凭空知道业务系统里的订单数据。

所以它还需要工具。

可以这样理解：

| LLM 职责 | 工具职责 |
|---|---|
| 理解和推理 | 执行真实动作 |
| 生成计划 | 连接外部系统 |
| 组织输出 | 获取实际数据 |

如果只有 LLM，没有工具，Agent 就只能停留在”建议”层面。

如果 LLM 能调用工具，它就可以真正连接外部系统。

## 三、Tool Calling 是 Agent 操作系统的手

Tool Calling，也叫工具调用，指的是让模型根据用户意图选择合适的外部工具。

例如我们可以给 Agent 提供几个工具：
```python
query_failed_orders(start_time, end_time)
summarize_order_errors(order_ids)
send_report_to_user(user_id, content)
```

当用户说：

> 帮我查一下上周失败的订单，并总结失败原因。

Agent 可能会执行：

1. 调用 query_failed_orders 查询失败订单
2. 调用 summarize_order_errors 汇总失败原因
3. 生成自然语言报告返回给用户

从后端角度看，Tool Calling 本质上就是：

> 把大模型的自然语言理解能力，连接到真实的后端函数、接口、数据库和业务系统。

这也是 Agent 工程落地的关键。

> **关键能力**：如果没有工具调用，模型只能”说”；有了工具调用，模型才能”做”。

### 工具调用不是随便开放接口

不过，Tool Calling 也不能简单理解为”把所有接口都丢给模型”。

真实系统中必须考虑：

- 这个用户有没有权限调用该工具
- 工具参数是否合法
- 是否需要二次确认
- 是否会修改重要数据
- 调用失败如何重试
- 调用过程是否需要审计日志
- 模型是否可能误调用危险接口

| 工具类型 | 风险等级 | 执行策略 |
|---|---|---|
| 查询类 | 低风险 | 可以自动执行 |
| 写入类 | 中风险 | 需要严格权限 |
| 高风险操作 | 高风险 | 需要人工确认 |

> **安全原则**：Tool Calling 的重点不只是”能调用”，还要”可控、安全、可审计”。

## 四、RAG 是 Agent 的外部知识库

LLM 的参数中虽然包含大量通用知识，但它不一定知道企业内部文档、项目规范、接口说明、历史会议纪要等私有知识。

这时就需要 RAG。

RAG 可以为 Agent 提供外部知识，例如：

- 公司内部文档
- 项目接口文档
- 用户手册
- 代码规范
- 历史工单
- 常见问题库
- 业务规则说明

可以这样理解：

| 组件 | 职责 |
|---|---|
| LLM | 推理和表达 |
| RAG | 提供外部知识 |
| Tool Calling | 执行外部动作 |

例如一个客服 Agent，可能需要：

- 通过 RAG 检索产品说明文档
- 通过 Tool Calling 查询用户订单状态
- 再由 LLM 组织成一段自然语言回复

这就是一个比较典型的 Agent 应用形态。

## 五、Memory 是 Agent 的长期上下文

普通 LLM 对话通常只依赖当前上下文窗口。

但是 Agent 如果要长期服务用户，就需要某种记忆能力。

Memory 可以分成几类。

| 记忆类型 | 说明 | 示例 |
|---|---|---|
| 短期记忆 | 当前会话上下文 | 前面说过"Go 后端项目" |
| 长期记忆 | 用户偏好、历史任务 | 用户主要使用 Go 语言 |
| 业务记忆 | 业务系统历史记录 | 历史订单、工单 |

### 1. 短期记忆

### 1. 短期记忆

短期记忆就是当前会话上下文。

例如用户前面说：

> 我现在在做一个 Go 后端项目。

后面又问：

> 那我应该怎么设计缓存？

模型需要知道”那”指的是前面的 Go 后端项目。

### 2. 长期记忆

长期记忆可以保存用户偏好、历史任务、项目背景等信息。

例如：

- 用户主要使用 Go
- 用户当前在做 RAG 项目
- 用户偏好用 MySQL + Redis + MQ 的后端架构

这样 Agent 后续回答时可以更加个性化。

### 3. 业务记忆

业务系统里的历史记录也可以作为一种记忆。

例如：

- 用户历史订单
- 历史客服工单
- 最近一次报表结果
- 项目任务执行记录

这些记忆通常不会直接塞进 Prompt，而是通过数据库、向量检索或工具调用按需读取。

## 六、Workflow 是 Agent 的任务执行流程

真实业务中的任务通常不是一步完成的。

例如：

> 帮我分析最近一周的用户反馈，找出主要问题，并生成一份报告。

这可能需要多个步骤：

1. 查询最近一周用户反馈
2. 按问题类型分类
3. 提取高频问题
4. 总结原因
5. 生成报告
6. 必要时发送给相关人员

这就是 Workflow。

在工程实现中，Workflow 可以是：

- 固定流程
- 状态机
- DAG 任务流
- 多 Agent 协作
- 人工审批 + 自动执行结合

对于后端开发者来说，Agent 的难点不只是”模型会不会回答”，而是：

- 工具调用是否安全
- 任务流程是否可控
- 执行失败能否重试
- 是否有权限校验
- 是否有日志和审计
- 是否可以中断、恢复和回滚
- 是否能监控成本和延迟

> **工程关键**：这些问题本质上都是工程问题，不是模型问题。

## 七、一个 Agent 系统可以怎么拆模块？

从后端工程角度看，一个 Agent 系统可以拆成这些模块。

> **架构原则**：模块化设计有助于职责分离、测试和维护。

### 1. 用户与权限模块

负责：

- 用户登录
- 角色权限
- 工具权限
- 知识库权限
- 操作审计

Agent 能不能调用某个工具，不能只由模型决定，还要由权限系统决定。

> **安全底线**：权限检查必须在工具调用前执行，不能让模型绕过权限系统。

### 2. 对话模块

负责：

- 会话管理
- 消息记录
- 上下文拼接
- 流式响应
- 多轮对话状态
### 3. RAG 知识库模块

负责：

- 文档上传
- 文档解析
- 文档切片
- Embedding
- 向量检索
- Rerank
- 引用来源返回
### 4. 工具调用模块

负责：

- 工具注册
- 参数校验
- 权限检查
- 工具执行
- 失败重试
- 调用日志
- 高风险操作确认
### 5. Workflow 模块

负责：

- 多步骤任务编排
- 状态流转
- 任务暂停与恢复
- 人工审批
- 失败处理
- 最终结果汇总
### 6. Memory 模块

负责：

- 短期上下文
- 长期用户偏好
- 历史任务记录
- 业务数据回查
- 按需召回记忆
### 7. 监控与成本模块

负责：

- 模型调用次数
- Token 消耗
- 接口耗时
- 工具调用成功率
- 用户反馈
- 错误日志
- 成本统计

这些模块组合起来，Agent 才会从 Demo 变成一个真正可用的系统。

## 八、后端开发者实现 Agent 时要注意什么？

### 1. 不要把 Agent 做成纯 Prompt 项目

如果一个项目只是写了几个 Prompt，然后调用模型返回结果，那工程价值会比较弱。

后端开发者应该重点体现：

- 数据流
- 工具调用
- 权限控制
- 异步任务
- 日志审计
- 稳定性设计
- 可观测性
- 成本控制

> **核心价值**：工程能力才是 Agent 项目真正的护城河。
### 2. 工具调用要可控

模型可能会理解错，也可能生成错误参数。

所以工具调用前必须做：

- 参数校验
- 权限校验
- 风险分级
- 必要时二次确认

| 工具类型 | 风险等级 | 执行策略 |
|---|---|---|
| 查询类工具 | 低风险 | 可以自动执行 |
| 写入类工具 | 中风险 | 需要严格权限 |
| 高风险工具 | 高风险 | 需要人工确认 |
### 3. 任务流程要可追踪

Agent 执行任务时，系统应该记录：

- 用户原始输入
- 模型决策过程
- 调用了哪些工具
- 工具参数是什么
- 返回结果是什么
- 是否失败
- 最终输出是什么

这样出了问题才能排查。

> **可观测性**：完整的执行日志是 Agent 系统可维护的基础。

### 4. 不要忽视权限和数据隔离

Agent 可以访问知识库和业务系统，这意味着权限非常重要。

必须保证：

- 用户不能检索无权限文档
- 用户不能调用无权限工具
- 不同租户数据不能串
- 高权限操作要有审计

> **安全原则**：权限检查必须后端硬控制，不能仅依赖模型的"理解"。
### 5. 要关注成本和延迟

大模型调用通常有成本，也有延迟。

所以系统要关注：

- Prompt 是否过长
- 是否重复调用模型
- 是否可以缓存
- 是否需要流式响应
- 是否需要小模型处理简单任务
- 是否需要异步执行长任务

这些都会影响用户体验和系统成本。

> **成本优化**：可以通过 Prompt 压缩、结果缓存、模型分级等方式降低成本。

## 九、从 RAG 到 Agent 的演进路线

如果要做一个项目，不建议一开始就做特别复杂的 Agent。

可以按下面路径逐步演进。

### 第一阶段：普通 LLM 对话

先实现：
```text
用户输入 → 调用 LLM → 返回回答
```

这个阶段主要熟悉模型 API、Prompt、流式响应。

### 第二阶段：RAG 知识库问答

再实现：
```text
文档入库 → Embedding → 向量检索 → LLM 基于资料回答
```

这个阶段开始体现后端工程能力。

### 第三阶段：Tool Calling

然后实现：
```text
用户自然语言请求 → LLM 判断工具 → 后端执行工具 → 返回结果
```

这时系统从”知识问答”升级为”执行任务”。

### 第四阶段：Memory + Workflow

最后加入：

- 长期记忆
- 多步骤任务
- 状态管理
- 审批流程
- 失败重试
- 监控告警

这个阶段才更接近完整 Agent 系统。

> **演进建议**：从简单到复杂，逐步验证每个阶段的价值，避免一开始就设计过于复杂的系统。

## 总结

Agent 可以理解为：

以 LLM 为核心，结合 RAG、Tool Calling、Memory 和 Workflow，能够理解任务、使用知识、调用工具并执行多步骤流程的智能系统。

### Agent vs 普通聊天机器人

| 对比项 | 普通聊天机器人 | Agent |
|---|---|---|
| 主要职责 | 回答问题 | 完成任务 |
| 能力范围 | 对话和文本生成 | 理解+检索+调用+执行 |
| 工具使用 | 无 | 支持工具调用 |
| 知识来源 | 模型内置参数 | 模型+外部知识库 |
| 复杂度 | 较低 | 较高 |

从工程角度看：

| 组件 | 职责 |
|---|---|
| LLM | 大脑 |
| RAG | 外部知识库 |
| Tool Calling | 操作系统的手 |
| Memory | 长期上下文 |
| Workflow | 任务执行流程 |
| 权限和监控 | 安全边界 |

对于后端开发者来说，Agent 开发不是脱离原有技术栈，而是在原有后端能力之上，加入大模型、向量检索、工具调用和任务编排。

这也是为什么 Agent 项目非常适合作为后端开发者切入 AI 应用方向的实践项目。
